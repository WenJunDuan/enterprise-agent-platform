# 项目落地路线

本文把主文档中的目标架构拆成分阶段实施路线，目的是让后续实现工作按固定顺序推进，而不是在多个业务域和多个入口上同时开工。

## 当前约束

- 当前仓库已经具备基础目录、最小 HTTP 服务链路和 CLI-only 的 `/init` 规则初始化骨架，但真实业务闭环仍未落地。
- 当前最缺的不是底座联通，而是费控域的真实样例规则、样例数据和正式结构化审核入口。
- 第一阶段优先做费控闭环样板链路，先覆盖差旅与招待。
- HR、legal、多租户、性能优化、独立部署文档暂不并行推进。

## 阶段顺序

### 阶段 1：仓库基础文件

目标：补齐仓库入口、基础配置和目录约定，让后续代码实现有清晰落点。

- 产物：`README.md`、`docs/` 文档入口层、`.env.example`、`pyproject.toml`、基础目录约定说明。
- 完成判定：新成员进入仓库后，能分清“当前现状”和“目标结构”，并知道后续实现顺序。
- 对应主文档：第 3 节、第 11 节。

### 阶段 2：`.claude/` 最小集

目标：先落地最小可调度框架和费控域关键 skill，而不是一次性写满所有 agents 和 commands。

- 产物：`.claude/CLAUDE.md`、`.claude/settings.json`、报销域 agent 集合、首批必要 skills。
- 范围：覆盖 `extractor -> auditor -> reviewer` 主链路，并补齐 `invoice-parse`、`pre-approval-match`、`travel-compliance`、`entertainment-compliance`、`budget-check`。
- 完成判定：调度规则能把费控类输入路由到差旅/招待分支，skills 与 hooks 的边界清晰。
- 对应主文档：第 4 节、第 5 节、第 6 节、第 9 节。

### 阶段 3：`knowledge/` Schema 与样例

目标：让规则读取和交叉比对都有真实数据来源，先打通费控闭环的最小知识库与样例数据。

- 产物：`knowledge/_schema/rule.schema.json`、`knowledge/expense/` 下差旅/招待/发票/预算样例规则、`data/pre-approvals/` 与 `data/invoices/` 样例数据。
- 范围：先准备报销域闭环样例，不在本阶段同时铺开 HR 和 legal 规则。
- 完成判定：`rule-query`、`invoice-parse`、`pre-approval-match` 与 `amount-validate` 可以基于真实 JSON 样例完成最小闭环验证。
- 对应主文档：第 6 节、第 8 节。

### 阶段 4：`server/` 最小运行链路

目标：实现一条最小可调用服务链，而不是同步完成所有接入形态的工程化细节。

- 产物：`server/core.py`、最小 CLI 或最小 HTTP 入口、必要环境变量读取。
- 范围：优先保证 `server/core.py` 到 Claude Agent SDK 的统一调用链成立，并能让报销单、发票和事前审批单在一次审核中关联起来；Chat REPL、SSE、Docker 支持可延后补齐。
- 完成判定：能通过一个最小入口完成差旅或招待样例审核，并返回结构化结果。
- 对应主文档：第 2 节、第 10 节、第 11 节。

### 阶段 5：`tests/` 最小测试集

目标：为费控闭环样板链路建立回归保护，满足“先测后码”的交付要求。

- 产物：覆盖文档约束、规则匹配、票据校验、事前事后匹配、服务入口和关键输出格式的最小测试集。
- 范围：先测差旅与招待两条主链路的关键约束，不要求一开始覆盖所有业务域与所有异常分支。
- 完成判定：新建实现至少具备文档校验、基础单元测试和一条费控闭环集成验证。
- 对应主文档：第 5 节、第 6 节、第 10 节。

## 首期明确不做

- 不同时展开 HR、legal 的完整 agent 与规则集。
- 不在第一轮就实现多租户隔离、完整并发优化或完整 Docker 交付。
- 不单独拆出 API 文档、部署手册、运维手册，直到实际代码和运行方式稳定。
