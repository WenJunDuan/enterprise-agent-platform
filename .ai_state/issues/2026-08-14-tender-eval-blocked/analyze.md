# 双根因

## Bug A（`server/tender/runner.py`）

1. `_DEFAULT_CONTEXT_MAX_BYTES = 64_000` 硬编码。该值按"最小窗口模型 64K token"反推，
   而实际部署是 **1M 窗口**——64 KB 只占 2%。**属派工前提错误（主 agent 给的假设），
   非上一轮实现错**。
2. `_bound_ocr_block` 保留前 N 字节**盲截**。招标文件的评标办法/评分标准**总在后部章节**，
   盲截必然优先砍掉最关键的一段。

两者叠加：底稿被截 39% 且截掉的正是评分标准。下游代价被 `AUDIT_MAX_TURNS=30` 放大成
整单无结论（模型试图靠反复 Read 补回被截内容，轮次先耗尽）。

## Bug B（`server/ocr/engine.py`）

1. **代理**：`NO_PROXY` 缺 OCR 域名，43 MB 穿代理中途断连（运维侧修 `.env`）。
2. **服务端拒绝大包**：`_post_multipart` 把整份读进内存一次性 POST；服务端对大包回
   `HTTP 400`（实测 50 页 OK / 80 页 400）。
3. **服务端限流**：连发无间隔 → 从第 3 片起全挂。
4. **`extract_pdf_subset` 的 `subset.save()` 不带压缩**，`insert_pdf` 逐页复制共享资源
   （字体/图片），子集反而比原文件大——独立 bug，混合 PDF 路径一直在吃这个亏。

## 共性

两者都属**"降级路径本身有缺陷"**：A 是预算闸降级时砍错内容，B 是大文件路径根本没有降级手段。

与同日上游事故（提示词重构爆窗）合起来看，三次故障都出在同一个模式上：
**主路径正常时无人验证降级路径，降级真的发生时才发现它是坏的。**
