# Learning · 交接档里的"已抢救/已转移"断言必须附实物证明

日期: 2026-08-19
类型: learning
来源 sprint: 2026-08-15-tender-context-pipeline（Step 3 case-2/3 沉淀）

## 一句话

handoff 记了「唯一副本已抢救至 `results-5ccbb361批-*.json`」，次日实查：**该文件从未存在于盘上**（全盘搜索无踪、服务器 task 表亦无该 request）；下游六步计划有两步把它当既定前提。

## 踩坑经过

1. 2026-08-18 深夜收口时，handoff/plan 双双记档"素材已抢救、含 criteria 回显 18,921 字"
2. 2026-08-19 Step 3 开工，标注 generator 按绝对路径读素材 → 文件不存在
3. 全盘 find + mdfind 无踪；服务器 `/tender/tasks` 全列表里也没有 5ccbb361
4. 连带发现第二处错记：`53f94fd0` 被当作BL晨跑结论引用，实测属**另一项目**
   （房建/市政类，criteria 与本项目零交集）——accuracy 计划的 D2 错位实证挂错了案主

## 为什么能挽回

删的是**项目**（级联删结论行），**任务行还活着**：`/tender/tasks/{id}/result` 对已删项目的任务仍可取。服务器直拉 4 条历史结论 + 现役 criteria，素材反而比"抢救件"更全。

## 规则

- 交接档写"已转移/已抢救/已备份 X"时，必须同行附**可复跑的验证命令与实测值**
  （`ls -la` 尺寸 / `sha256sum` / 行数），与 doc-style「量化基线必附测量命令」同源
- 引用某结论 JSON 作为某案主的素材前，先核 `criteria` 与项目字段是否对得上——
  request_id 不含语义，**凭 id 引用等于凭印象引用**
- 数据"删库"结论下得早了：级联删除的边界要实测（本例任务行幸存），
  抢救优先级排在"从活系统直拉"之后

## 第二次发生（2026-08-20，同一形态）

`handoff-2026-08-19.md` 三节写下"下会话第一件事 = 核任务 `d82aca89`（项目 `tp-7bbe…`）"，
并称它"会话结束时在跑"。次日核查：**该任务与该项目在部署机上均不存在**
（线上实存 4 项目 / 6 任务，逐条比对）。真正可核的是同案另一单，也正是 v2.2 拿去做
双跑对照的那份报告——即写 handoff 时手边就有正确 id，写下的却是另一个。

**这条教训写下来一天后又犯了一次**，说明"写时自觉"不成立。故加一条机械要求：

- **交接档里的任何 id（task/project/commit/文件名），落笔时必须是从工具输出复制的，
  不能是回忆或推断**；无法当场复制的（如"正在跑"的任务）→ 写成"待核：用
  `GET /tender/tasks?limit=N` 找 <特征描述>"，**不要写一个具体 id**——
  一个错的具体 id 比一句"待核"更贵，因为它看起来可信、会被下游直接引用。
