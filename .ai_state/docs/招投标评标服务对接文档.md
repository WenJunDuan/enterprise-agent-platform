# 招投标评标服务对接文档

> 面向前端与第三方系统。与 `前端审核服务对接文档.md`（报销审核 / OCR）互补，本文只覆盖 `/tender/*`。
> 接口以 `server/routes/tender/` 源码为准；本文档给出的字段来自 pydantic 模型与实际返回体。

---

## 1. 接口总览

所有接口前缀 `/tender`，均需 Bearer 鉴权（`GET /health` 除外）。

| # | 方法 | 路径 | 用途 | 同步性 |
|---|---|---|---|---|
| **项目** |
| 1 | POST | `/tender/projects` | 建招标项目（幂等） | 同步 |
| 2 | GET | `/tender/projects` | 项目列表 | 同步 |
| 3 | GET | `/tender/projects/{project_id}` | 项目详情 + 投标人名册 | 同步 |
| 4 | DELETE | `/tender/projects/{project_id}` | 级联删除项目 | 同步 |
| **文档上传与预处理** |
| 5 | POST | `/tender/projects/{project_id}/tender-doc` | 上传招标文件，触发 OCR + 评分标准抽取 | 异步 |
| 6 | POST | `/tender/projects/{project_id}/bids` | 上传一家投标文件，触发 OCR | 异步 |
| 7 | GET | `/tender/projects/{project_id}/tender-doc` | 招标文件状态 + 抽取出的评分标准 | 同步 |
| 8 | GET | `/tender/projects/{project_id}/docs-status` | 轮询：招标层 + 各投标层 OCR 状态 | 同步 |
| **评标** |
| 9 | POST | `/tender/projects/{project_id}/evaluate` | 提交一家投标评标 | 异步 |
| 10 | POST | `/tender/evaluate` | 旧入口，不挂项目（兼容保留） | 异步 |
| 11 | GET | `/tender/tasks` | 评标任务列表 | 同步 |
| 12 | GET | `/tender/tasks/{request_id}` | 单任务状态（轮询用） | 同步 |
| 13 | GET | `/tender/tasks/{request_id}/result` | 评标完整结论 | 同步 |
| 14 | POST | `/tender/tasks/{request_id}/retry` | 重跑 | 异步 |
| 15 | DELETE | `/tender/tasks/{request_id}` | 删任务 | 同步 |
| **结果回看** |
| 16 | GET | `/tender/projects/{project_id}/results` | 该项目全部结论摘要 | 同步 |
| 17 | GET | `/tender/projects/{project_id}/results/{request_id}` | 单条完整结论（删任务后仍可取） | 同步 |
| **价格横比** |
| 18 | POST | `/tender/projects/{project_id}/compare` | 触发 / 重跑横比 | 异步 |
| 19 | GET | `/tender/projects/{project_id}/compare` | 横比生命周期 + 结果 | 同步 |

## 2. 准备

### base URL & 鉴权

```
生产: http://100.91.100.13:9999
本地: http://127.0.0.1:9999
```

所有请求带：

```http
Authorization: Bearer <TENANT_TOKEN>
```

token 由服务端 `TENANT_KEYS` 环境变量配置，一个 token 对应一个 tenant，数据按 tenant 隔离。

| 情况 | 状态码 | 说明 |
|---|---|---|
| 缺 Authorization 头 | 401 | `Missing Authorization header` |
| 非 Bearer 格式 | 401 | `Authorization header must use Bearer token` |
| token 无效 | 401 | `Invalid tenant token` |
| 服务端未配置 TENANT_KEYS | 503 | 运维问题，非调用方问题 |

> 开发环境可设 `ALLOW_INSECURE_DEFAULT_TENANT_KEY=1` 免鉴权，此时 tenant 恒为 `default`。**生产禁用**。

### CORS

浏览器直连需服务端 `CORS_ALLOWED_ORIGINS` 白名单包含你的 origin（协议+域名+端口完全一致）。第三方服务端对接不受此限。

### 支持的文件格式

`.pdf .doc .docx .xls .xlsx .xlsm .xlsb .ppt .pptx .odt .ods .odp .txt .md .csv .tsv .json .png .jpg .jpeg .bmp .tif .tiff .webp`

不在清单内的后缀在上传阶段即被拒（400）。

## 3. 推荐调用流程

```
① POST /tender/projects                         → project_id
② POST /tender/projects/{id}/tender-doc         → 上传招标文件（异步 OCR + 评分标准抽取）
③ 轮询 GET /tender/projects/{id}/docs-status    → 等 tender_doc.criteria_status = ready
   （可用 GET /tender/projects/{id}/tender-doc 取回抽出的 criteria 让用户确认/修正）
④ POST /tender/projects/{id}/bids               → 每家一次，各得一个 bid_id（异步 OCR）
⑤ 轮询 GET /tender/projects/{id}/docs-status    → 等各 bid 的 ocr_status = ready
⑥ POST /tender/projects/{id}/evaluate           → 每家一次，得 request_id
⑦ 轮询 GET /tender/tasks/{request_id}           → 等 status = completed
⑧ GET  /tender/tasks/{request_id}/result        → 取该家结论
⑨ 全部家评完后 GET /tender/projects/{id}/compare → 价格横比 + 排名 + 推荐中标人
```

**关键约束**

- ③ 必须等到 `criteria_status = ready` 再评标。评分标准没抽出来就评标，结论无评分项依据。
- ⑤ 投标 OCR 未 ready 就提交评标会走 inline OCR 慢路径（多耗数分钟），且质量更差。
- ⑥ 提交时 **必须** 在 `form_json` 里带上 ④ 返回的 `bid_id`，否则复用不到已预热的底稿。
- ⑨ 横比要求 ≥2 家已完成评标。评标终态会自动入队横比，⑱ 只是重跑入口。

## 4. 接口详情

### 4.1 `POST /tender/projects` — 建招标项目

**请求体**（`application/json`，全部字段可选）

```json
{
  "scenario": "expert_assist",
  "tender_no": "YCTACG2024-Z01-2",
  "title": "盐城涉案车辆管理系统建设项目",
  "tenderee": "采购人YC交通警察支队",
  "method": "综合评分法",
  "control_price": "500000",
  "funding_type": "state_funded"
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `scenario` | enum | `bidder_self_check`（投标人自检）/ `expert_assist`（评委辅助）/ `post_eval_monitor`（事后监督）。默认见服务端 `DEFAULT_PROJECT_SCENARIO` |
| `tender_no` | string? | 招标编号。**幂等键**：同 tenant + 同 tender_no 重复调用返回已存在的项目，不新建 |
| `title` | string? | 项目名称 |
| `tenderee` | string? | 招标人 |
| `method` | string? | 评标方法 |
| `control_price` | string? | 最高限价 / 预算 |
| `funding_type` | string? | `state_funded` / `other` / `unknown`。影响横比推荐中标人的终局护栏 |

**响应 200**

```json
{
  "project_id": "tp-774462160ed5428b",
  "scenario": "expert_assist",
  "tender_no": "YCTACG2024-Z01-2",
  "title": "盐城涉案车辆管理系统建设项目",
  "tenderee": null,
  "method": null,
  "control_price": null,
  "funding_type": null,
  "status": "active",
  "created_at": "2026-08-18T04:00:00Z",
  "updated_at": "2026-08-18T04:00:00Z"
}
```

### 4.2 `GET /tender/projects` — 项目列表

**Query**：`status`（可选）、`scenario`（可选）、`limit`（1–100，默认 20）、`offset`（默认 0）

**响应 200**：`TenderProjectResponse[]`，结构同 4.1。

---

### 4.3 `GET /tender/projects/{project_id}` — 项目详情 + 投标人名册

**响应 200**（在 4.1 基础上追加）

```json
{
  "project_id": "tp-774462160ed5428b",
  "...": "同 4.1 全部字段",
  "bidder_count": 2,
  "bids": [
    {
      "request_id": "5ccbb361-ecea-4a59-92a3-f0352a14477b",
      "claim_id": "投标人YD",
      "bidder_name": "投标人YD",
      "status": "completed",
      "verdict": "manual_review"
    },
    {
      "request_id": "83177b56-ab4a-4dbb-a96c-4de8ebe9b607",
      "claim_id": "投标人BL",
      "bidder_name": "投标人BL",
      "status": "running",
      "verdict": null
    }
  ],
  "recommended_bidder": null,
  "compare_stale": false
}
```

| 字段 | 说明 |
|---|---|
| `bids[].status` | `accepted` / `running` / `completed` / `failed` |
| `bids[].bidder_name` | 手填优先（上传投标文件时填的），无手填则回退 agent 从结论识别的名称 |
| `bids[].verdict` | 仅 completed 有值：`approved` / `rejected` / `manual_review` |
| `recommended_bidder` | **仅当**横比已跑完、未过期（`compare_stale=false`）、且是终局结论（非 provisional）才有值；否则 null |
| `compare_stale` | true = 横比跑过但参与集已变（新增/删除了投标人），需重跑 |

名册 = 已完成结论（`results`）∪ 在途任务（`tender_tasks`）。**删任务不会让已完成的投标人从名册消失。**

---

### 4.4 `DELETE /tender/projects/{project_id}` — 级联删除

删除项目及其全部投标任务、结论、横比结果、上传文件目录，并停掉该项目在跑的 OCR。

| 状态码 | 条件 |
|---|---|
| 200 | 删除成功 |
| 404 | 项目不存在 |
| 409 | 项目下有在途（accepted/running）评标任务，或有在途横比任务 |

**响应 200**

```json
{ "project_id": "tp-xxx", "status": "deleted", "deleted": { "tasks": 3, "results": 2, "compare": 1 } }
```

---

### 4.5 `POST /tender/projects/{project_id}/tender-doc` — 上传招标文件

**请求**：`multipart/form-data`

| 字段 | 说明 |
|---|---|
| `files` 或 `file` | 一个或多个文件（可重复该字段名传多份）。**至少 1 个**，否则 400 |

**响应 200**（立即返回，不等 OCR）

```json
{ "project_id": "tp-774462160ed5428b", "ocr_status": "running" }
```

后台异步：OCR 识别 → 抽取评分标准（criteria）与招标基本信息（tender_info）。用 4.7 / 4.8 轮询。

| 状态码 | 条件 |
|---|---|
| 400 | 无文件 / 文件格式不支持 / 上传连接中断 |
| 404 | 项目不存在 |

---

### 4.6 `POST /tender/projects/{project_id}/bids` — 上传投标文件

**请求**：`multipart/form-data`

| 字段 | 说明 |
|---|---|
| `files` / `file` | 该投标人的全部投标文件。**至少 1 个** |
| `bidder_name` | 可选。投标单位名称，填了则在名册中优先展示此名 |

**响应 200**

```json
{ "bid_id": "bd-70b2acb9820f43d9", "ocr_status": "running" }
```

> **`bid_id` 必须由前端保存**，提交评标（4.9）时回传，否则评标会重跑一遍 OCR（实测多耗约 5 分钟）。

---

### 4.7 `GET /tender/projects/{project_id}/tender-doc` — 招标文件信息 + 评分标准

**响应 200**

```json
{
  "ocr_status": "ready",
  "ocr_clarity": "high",
  "criteria_status": "ready",
  "criteria": {
    "eligibility_rules": [
      { "id": "ELG-01", "check": "具有独立承担民事责任的能力", "requirement": "提供营业执照等证明文件", "source": "招标文件第二章 2.1" }
    ],
    "items": [
      { "item": "投标报价", "max": 30, "category": "价格", "basis": "低价优先法，评标基准价取有效最低报价", "score_mode": "formula" },
      { "item": "投标供应商实力", "max": 10, "category": "商务", "basis": "软件企业证书/体系认证/著作权各加分", "score_mode": "additive" }
    ],
    "total_max": 100
  },
  "tender_info": { "project_name": "...", "budget": "500000", "method": "综合评分法" },
  "tender_files": ["招标文件.pdf"]
}
```

| 字段 | 取值 | 说明 |
|---|---|---|
| `ocr_status` | `pending` / `running` / `ready` / `degraded` / `partial` / `failed` | `degraded`=用了本地兜底引擎；`partial`=部分文件失败或缺页。两者仍可评标但质量下降 |
| `ocr_clarity` | `high` / `low` / `unknown` / null | 识别清晰度 |
| `criteria_status` | `pending` / `running` / `ready` / `failed` | 评分标准抽取状态 |
| `criteria` | object / null | 抽取出的资格审查规则 + 评分项。**`criteria_status != ready` 时不可信** |

> 服务端兜底：`ocr_status=failed` 且 `criteria_status` 还停在 pending/running 时，对外强制返回 `failed`，让前端能停止轮询。

| 状态码 | 条件 |
|---|---|
| 404 | 项目不存在，或该项目尚未上传招标文件 |

### 4.8 `GET /tender/projects/{project_id}/docs-status` — 轮询总入口

**响应 200**

```json
{
  "tender_doc": {
    "ocr_status": "ready",
    "criteria_status": "ready",
    "criteria_error": null
  },
  "bids": [
    { "bid_id": "bd-70b2acb9820f43d9", "bidder_name": "投标人YD", "ocr_status": "ready" },
    { "bid_id": "bd-ced3e159cff44d1a", "bidder_name": "投标人BL", "ocr_status": "running" }
  ]
}
```

- `tender_doc` 为 null = 尚未上传招标文件。
- `criteria_error`：`criteria_status=failed` 时的具体原因，应展示给用户（不要只显示"识别失败"）。

**建议轮询间隔 3–5 秒**；大标书 OCR 通常需要 1–5 分钟。

---

### 4.9 `POST /tender/projects/{project_id}/evaluate` — 提交评标

两种提交方式二选一。

**方式 A（推荐）：multipart 上传 + 复用预热底稿**

```
Content-Type: multipart/form-data

mode=upload
form_json={"bid_id":"bd-70b2acb9820f43d9","bidder_name":"投标人YD"}
files=<该投标人的文件…>
```

`form_json` 里的 `bid_id` 来自 4.6。缺 `bid_id` 时服务端会按 `bidder_name` 回查预热记录；两者都缺则退回 inline OCR 慢路径。

**方式 B：指向已存在的服务端目录**

```json
{ "mode": "directory", "directory_path": "<服务端 case 目录>" }
```

路径受白名单校验，必须落在本 tenant + 本 project 的 submission 目录下。

**响应 200**

```json
{
  "request_id": "5ccbb361-ecea-4a59-92a3-f0352a14477b",
  "status": "accepted",
  "mode": "upload",
  "task_status_url": "/tender/tasks/5ccbb361-ecea-4a59-92a3-f0352a14477b"
}
```

| 状态码 | 条件 |
|---|---|
| 400 | `mode` 不是 upload / 上传中断 |
| 404 | 项目不存在 |
| 415 | Content-Type 既非 json 也非 multipart |
| **503** | **评标队列已满**（在途任务达上限），稍后重试 |

### 4.10 `POST /tender/evaluate` — 旧入口

同 4.9，但不挂招标项目（`project_id=null`）。结论不会出现在 `/projects/{id}/results` 里，也不参与横比。**新对接不要用。**

### 4.11 `GET /tender/tasks` — 任务列表

**Query**：`status`、`limit`（1–100，默认 20）、`offset`

**响应 200**：`TenderTaskStatusResponse[]`，结构见 4.12。

---

### 4.12 `GET /tender/tasks/{request_id}` — 任务状态（轮询）

**响应 200**

```json
{
  "request_id": "5ccbb361-ecea-4a59-92a3-f0352a14477b",
  "status": "running",
  "mode": "upload",
  "claim_id": "投标人YD",
  "error_detail": null,
  "progress_message": "S3 正在逐项评分…",
  "submitted_at": "2026-08-18T04:16:52Z",
  "started_at": "2026-08-18T04:16:55Z",
  "finished_at": null,
  "updated_at": "2026-08-18T04:20:11Z"
}
```

| status | 含义 |
|---|---|
| `accepted` | 已受理，排队中 |
| `running` | 评标中，`progress_message` 实时反映模型进展 |
| `completed` | 完成，可取结果 |
| `failed` | 失败，看 `error_detail` |

**建议轮询间隔 5 秒**。单家评标实测 3–13 分钟，服务端软超时 `TENDER_TIMEOUT_SEC`（生产 1200 秒）。

### 4.13 `GET /tender/tasks/{request_id}/result` — 评标结论

| 状态码 | 条件 |
|---|---|
| 200 | 成功 |
| 404 | 任务不存在，或结论不存在 |
| **409** | **任务尚未 completed** |

**响应 200**（完整结构见 §5）

---

### 4.14 `POST /tender/tasks/{request_id}/retry` — 重跑

原子状态转移，并发双击只有一次成功。重跑保留原 `project_id` 归属。

| 状态码 | 条件 |
|---|---|
| 200 | 已重新排程，返回最新任务状态 |
| 400 | 该任务没有可重跑的源路径 |
| 404 | 任务不存在 |
| 409 | 任务仍在运行 |
| 503 | 队列已满 |

---

### 4.15 `DELETE /tender/tasks/{request_id}` — 删任务

删任务记录 + 上传目录。**已完成的结论不会被删**，仍可通过 4.17 取回。

| 状态码 | 条件 |
|---|---|
| 200 | `{"request_id": "...", "status": "deleted"}` |
| 404 | 任务不存在 |
| 409 | 任务运行中，删不动 |

---

### 4.16 `GET /tender/projects/{project_id}/results` — 结论摘要列表

**Query**：`limit`（1–200，默认 50）、`offset`

**响应 200**

```json
[
  {
    "request_id": "5ccbb361-ecea-4a59-92a3-f0352a14477b",
    "claim_id": "投标人YD",
    "bidder_name": "投标人YD",
    "verdict": "manual_review",
    "manual_review_reason": "insufficient_evidence",
    "created_at": "2026-08-18T04:24:28Z"
  }
]
```

**独立于任务表**——删任务后这里仍然有。

---

### 4.17 `GET /tender/projects/{project_id}/results/{request_id}` — 单条完整结论

与 4.13 返回同样的结构，但**不依赖任务是否还存在**。做历史回看用这个，不要用 4.13。

| 状态码 | 条件 |
|---|---|
| 404 | 项目不存在，或该结论不属于此项目 |

---

### 4.18 `POST /tender/projects/{project_id}/compare` — 触发价格横比

评标完成会**自动**入队横比；本端点是"重新横比"按钮的入口。

| 状态码 | 条件 |
|---|---|
| 200 | 已排程 |
| 400 | 已完成评标的投标人不足 2 家 |
| 404 | 项目不存在 |
| 409 | 该项目横比正在进行中 |

---

### 4.19 `GET /tender/projects/{project_id}/compare` — 横比结果

**恒返回 200**（项目不存在时 404），用 `status` 字段判生命周期。

```json
{
  "project_id": "tp-774462160ed5428b",
  "status": "ready",
  "error_detail": null,
  "result": {
    "project_id": "tp-774462160ed5428b",
    "method": "综合评分法",
    "bidders": [
      { "claim_id": "投标人YD", "price": 462800, "price_score": 30, "other_score": 45, "total_score": 75, "rank": 1 },
      { "claim_id": "投标人BL", "price": 458000, "price_score": 30, "other_score": 40, "total_score": 70, "rank": 2 }
    ],
    "recommended": "投标人YD",
    "provisional": false,
    "warnings": [],
    "explanation": "……",
    "policy_refs": ["tender_evalmethod_003"],
    "evidence_chain": []
  },
  "stale": false,
  "computed_at": "2026-08-18T05:00:00Z",
  "input_result_ids": ["5ccbb361-…", "83177b56-…"]
}
```

| status | 含义 |
|---|---|
| `none` | 从未跑过 |
| `pending` | 已入队 |
| `running` | 计算中 |
| `ready` | 有结果 |
| `failed` | 最近一次失败，`error_detail` 是**脱敏后**的原因（无堆栈、无服务器路径） |

- 在途状态**优先于**已有结果：能同时展示旧结果 + "正在重算"。
- `stale=true`：结果基于的投标人集已变，需重跑。
- `provisional=true`：非终局推荐（例如尚有未完成的评标 / 缺关键数据），**不得据此定标**。
- `recommended` 可能为 null。

### `pending_reason` 取值（`score=null` 时必填）

| 值 | 含义 | 前端应如何展示 |
|---|---|---|
| `cross_bid` | 需全部投标报价汇总后横比才能算 | "待横比"，等 4.19 出结果后补上 |
| `external_data` | 需外部数据（信用中国查询等） | "待外部核验" |
| `live_event` | 需现场答辩 / 演示评分 | "待现场评审"，引导录入现场分 |
| `evidence_unresolved` | 底稿里找不到 / 读不清对应证据 | **"待人工调阅原件"**，附 `basis` 里的定位线索 |
| `manual_mode` | 该评分项本身就是人工主观项 | "待评委打分" |
| `non_responsive` | 实质性不响应，无可评事实 | 按废标 / 不得分处理，看 `basis` |

> **重要：`score=null` 一律不等于 0 分。** 系统设计上明确禁止在证据缺失时判 0。前端不得把 null 渲染成 0，也不得把 null 计入合计。

### 已知字段缺口

- `extracted_data.total_score` / `total_max` **当前不会被填充**（schema 未强制，模型也不产出）。总分需前端按 `scoring[]` 自行汇总，且必须排除 `score=null` 的项并单独提示"N 项待定、共 M 分未计"。
- `extracted_data.bidder_name` 常为空；投标人名称请取顶层 `claim_id`，或 4.3 名册里的 `bidder_name`。

const BASE = 'http://100.91.100.13:9999';
const TOKEN = import.meta.env.VITE_TENDER_TOKEN;

async function api<T>(path: string, init: RequestInit = {}): Promise<T> {
  const res = await fetch(`${BASE}${path}`, {

export async function pollTask(
  requestId: string,
  onProgress?: (t: TenderTask) => void,
  intervalMs = 5000,
): Promise<TenderTask> {
  for (;;) {
    const t = await taskStatus(requestId);
    onProgress?.(t);
    if (t.status === 'completed' || t.status === 'failed') return t;
    await new Promise((r) => setTimeout(r, intervalMs));
  }
}

## 7. 错误处理

| 状态码 | 场景 | 前端处理 |
|---|---|---|
| 400 | 无文件 / 格式不支持 / 上传中断 / 横比不足 2 家 | 展示 `detail`，可重试 |
| 401 | 鉴权失败 | 跳登录 / 检查 token 配置 |
| 404 | 项目、任务或结论不存在 | 刷新列表 |
| 409 | 任务未完成就取结果 / 删或重跑运行中的任务 / 横比进行中 / 项目有在途任务 | **不是错误**，提示"处理中，请稍候"并继续轮询 |
| 415 | Content-Type 不对 | 代码问题 |
| **503** | **评标队列已满** | 指数退避重试，不要立即重发 |
| 500 | 服务端异常 | 展示通用错误，记录 request_id 供排查 |

错误响应体统一为 FastAPI 形态：

```json
{ "detail": "评标队列已满，请稍后重试" }
```

## 8. 对接自检清单

- [ ] 所有请求带 `Authorization: Bearer <token>`
- [ ] 上传文件字段名是 `files`（多份重复该字段），不是 `file[]`
- [ ] 上传投标返回的 `bid_id` 已保存，并在提交评标时通过 `form_json` 回传
- [ ] 提交评标前已确认 `criteria_status === 'ready'`
- [ ] 提交评标前已确认该 bid 的 `ocr_status` 为 ready / degraded / partial（不是 running / pending）
- [ ] 任务轮询用 `GET /tender/tasks/{id}`，间隔 ≥5 秒，处理 `failed` 分支
- [ ] 取结果时处理 409（未完成）而不是当作错误
- [ ] `scoring[].score === null` 渲染为"待定 + pending_reason 文案"，**绝不显示 0 分**
- [ ] 总分自行汇总，并明确标出"N 项待定、共 M 分未计入"
- [ ] `recommended_bidder` 只在 `compare_stale === false` 且 `provisional === false` 时展示
- [ ] 提交评标处理 503（队列满）并退避重试
- [ ] 历史回看走 `/projects/{id}/results/{request_id}`，不走 `/tasks/{id}/result`
