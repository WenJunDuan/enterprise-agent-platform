# A-008 自审：README 重写与命令面收口

## 结论

- VERDICT: PASS

## 本轮问题

1. 原 README 信息完整，但高频入口不够靠前
   - “怎么启动”
   - “端口在哪配”
   - “CLI 有哪些命令”
   - “后台服务怎么查状态”
   这些内容都存在，但需要连续滚动多段后才能拼出来。
2. 文档结构更像“顺叙教程”，不够像“工作台手册”
   - 新同事第一次进入仓库时，更需要的是速查，而不是从头读到尾。

## 实际改动

- 重写 `README.md`
  - 将结构调整为：
    - 快速开始
    - 端口与地址
    - 命令总览
    - 环境变量
    - HTTP API
    - 审核流程
    - 查询与追溯
    - 错误返回
    - 部署
    - 测试与排障
    - 目录结构
  - 将 `python -m server.cli` 与 `app-server` 分开讲，避免“业务 CLI”和“进程管理 CLI”混淆
  - 将 `APP_SERVER_HOST` / `APP_SERVER_PORT` 与 `app-server status` 提前，便于快速定位当前端口
  - 保留原先关键能力说明，但删除了大量重复铺垫

## 校验

- `uv run python -m server.cli --help`
- `uv run app-server --help`
- `uv run app-server doctor --help`

以上命令均已实际执行，用来确认 README 中的关键命令和参数名与当前实现一致。

## 为什么这样更合适

1. README 首屏应该先服务“第一次启动项目的人”。
2. 端口、命令和 HTTP 面是最高频信息，应该在前 1/3 内出现。
3. 详细的前端接入细节已经有独立文档，README 不需要再承担全部说明书角色。

## 风险与遗留

- 这轮重写没有改变前端对接文档和更细的制度治理文档，只调整仓库主入口 README。
- README 里的 curl 示例仍然默认使用 `127.0.0.1` 访问；如果部署在远端机器，需要按实际网关或反向代理地址替换。

## 下一步建议

- 如果后续还要继续优化文档体验，优先考虑补一个简短的 `docs/ops-runbook.md`
- 如果前端接入会长期由多人维护，可以继续把“查询接口字段速查表”单独抽成一页
